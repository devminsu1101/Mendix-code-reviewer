# Mendix Code Reviewer

Mendix 앱의 **모델 자체를 프로그래밍적으로 읽어** 성능·구조·보안 결함을 찾아내고,
"어디부터 손대야 하는가"를 우선순위와 근거로 정리해 주는 정적 분석 도구입니다.

---

## 1. 왜 만들었나

Mendix 프로젝트는 소스가 전부 바이너리입니다(`.mpr` = SQLite, `mprcontents/**/*.mxunit`).
그래서 일반적인 개발 도구가 통하지 않습니다.

| 일반 코드베이스 | Mendix |
| :--- | :--- |
| `git diff`로 변경 내용 확인 | ❌ 바이너리라 diff 불가 |
| `git blame`으로 도입 시점 추적 | ❌ 파일 단위 diff 자체가 없음 |
| ESLint / SonarQube 같은 정적 분석 | ❌ 텍스트 소스가 없어 적용 불가 |
| 코드 리뷰(PR diff) | ❌ 볼 것이 없음 |

결과적으로 **"무엇이 바뀌었는지" 아는 유일한 경로가 커밋 메시지**인데,
실제 이력을 조사해 보니 상당수가 `수정` / `commit` 수준이라 추적이 성립하지 않았습니다.

→ **사람의 기록에 의존하지 말고, 모델에서 직접 사실을 뽑아내자.**
이것이 이 도구의 출발점입니다.

---

## 2. Studio Pro의 Errors 창과 뭐가 다른가

가장 먼저 받는 질문이라 앞에 둡니다. 한 줄로 답하면:

> **Studio Pro의 Errors 창은 "이 모델이 유효한가(돌아가는가)"를 묻고, 이 도구는 "이 모델이 건강한가, 어디부터 고쳐야 하는가"를 묻습니다.**

컴파일러/린터와 코드 리뷰어의 차이라, 겹치는 영역이 거의 없습니다.

| | Studio Pro Errors 창 | Mendix Code Reviewer |
| :--- | :--- | :--- |
| 묻는 것 | 이 모델이 **배포 가능한가** | 이 모델이 **운영에서 버티는가** |
| 판정 성격 | 일관성 검사 — 참조 깨짐, 타입 불일치, 필수 속성 누락 | 품질 판정 — 성능, 아키텍처, 보안 정책, 팀 컨벤션 |
| 판정 범위 | 대체로 **문서 하나 안에서 닫힘** | **모델 전체 그래프** 위에서 판정 |
| 우선순위 | 평평한 목록 (문서 순) | 결함 심각도 × **진입점 위험 가중치** |
| 보는 대상 | 내 로컬 작업 카피 | Team Server의 **임의 브랜치·임의 커밋** |
| 실행 주체 | Studio Pro를 연 사람만 | 헤드리스 (CI·스케줄·웹훅) |
| 산출물 | IDE 창 (닫으면 사라짐) | Markdown 파일 (이력 축적, 공유 가능) |
| 과거 조회 | 불가 | **가능** — 과거 커밋 모델을 열어 재판정 (`--blame`) |
| 규칙 정의 | Mendix가 정함 | **우리가 정함** (`rules.ts`) |

### 이 도구가 잡는 것은 전부 "유효한 모델"이다

- 루프 안 DB Retrieve → 정상 동작합니다. 느릴 뿐입니다.
- 조회 키에 인덱스 없음 → 정상 동작합니다. 풀스캔일 뿐입니다.
- 액션 40개짜리 마이크로플로우 → 정상 동작합니다. 아무도 못 고칠 뿐입니다.

**"잘못 쓴 것"이 아니라 "느리게·위험하게 쓴 것"**이라 애초에 컴파일러의 관심사가 아닙니다.
실측 리포트에서 161건이 나온 그 브랜치는 **Studio Pro 에러 0건 상태로 이미 배포된 코드**였습니다.
그중 최상단에 오른 `ACT_SABIS_DataMigration_2_withAir`(3단 중첩 루프 + 루프 내 커밋 + 액션 과다, 144점)는
Studio Pro 기준 경고 0건입니다.

### 전체 그래프가 없으면 판정 자체가 불가능한 규칙들

| 규칙 | 필요한 것 |
| :--- | :--- |
| L006 고아 flow | 진입점 11종 전체에서 BFS 도달성 |
| L008 중복 로직 | 전체 flow 419개의 지문 비교 |
| D003 인덱스 누락 | 모든 XPath 조회 키 ↔ 도메인 모델 인덱스 정의 교차 |
| D006 파급 반경 | 이 엔티티를 만지는 flow 전수 집계 |
| D007 모듈 결합 | 모듈 간 참조 전량 |

Studio Pro에도 Find usages가 있지만 **한 문서씩 사람이 눌러야** 하고, "이 flow가 어떤 스케줄 이벤트에서 몇 단계 아래에 있는가"까지는 말해주지 않습니다.
실측에서 나온 **고아 flow 40개**는 사람이 419개 문서에 Find usages를 419번 눌러야 얻는 숫자입니다.

### 반대로, Studio Pro가 하는 것은 이 도구가 하지 않는다

- **모델 유효성 검사는 안 합니다.** 참조 깨짐·타입 오류는 Studio Pro의 몫이고 이미 잘 하고 있습니다. 중복 구현할 이유가 없습니다.
- **실시간이 아닙니다.** Studio Pro는 타이핑 즉시, 이 도구는 수 분 걸립니다. 하나는 작성 중 피드백, 하나는 사후 감사로 용도가 다릅니다.
- **더블클릭 점프가 안 됩니다.** 리포트에는 qualified name 텍스트만 있습니다.
- **오탐이 있을 수 있습니다.** Studio Pro는 메타모델 기반이라 전량 정확하지만 이 도구는 휴리스틱입니다.
  그래서 "병목을 단정하지 않고 정렬 축을 공개한다"(§5-6)는 설계를 넣었습니다.
- 보안 관련 일부 항목(페이지 역할 미지정 등)은 Studio Pro의 보안 검사와 **부분적으로 겹칠 수 있습니다.**

> 한 문장으로: Studio Pro는 **"이거 실행됩니까?"**에 답하고,
> 이 도구는 **"이거 데이터 10배 늘면 터집니까? 누가 언제 넣었습니까? 뭐부터 고칩니까?"**에 답합니다.

## 3. 무엇을 하는가

Team Server에서 지정한 브랜치의 모델을 열어, 전체를 순회하며 다음을 산출합니다.

- **관계 그래프**: 마이크로플로우 호출 그래프, 진입점(스케줄·공개 서비스·엔티티 이벤트·페이지 등)에서의 도달성, 엔티티 사용 현황, XPath 조회 키 인덱스
- **규칙 위반 탐지**: 로직 8종 / 도메인·보안 7종 / 페이지 2종 (총 17개 규칙)
- **우선순위 점수**: 결함 자체의 심각도 × **어디서 실행되는가**(진입점 위험 가중치)
- **Markdown 리포트**: 규칙별 조치 지시 + 인덱스 작업 지시서 + 모듈별 건강도
- **도입 시점 역추적(`--blame`)**: 이 결함이 언제·어느 커밋에서 들어왔는가
- **AI 온보딩 가이드**: 모델 메타데이터를 근거로 신규 투입자용 프로젝트 안내서 생성 (Gemini)

### 실행 예시 (실측 규모: flow 419개 / 모듈 20여 개)

```
🗺️ 모델 구성
- 리뷰 대상 flow 356개 (전체 419개) — 도달 가능 316개 / 고아 40개
- 제외된 모듈 11개 (마켓플레이스·테마, 수정 대상 아님)
- 진입점 399개 — ScheduledEvent 2, PublishedService 8, Navigation 29, Page 360

📊 이슈 161건 (🔴 29 / ⚠️ 132)
```

## 5. 설계에서 신경 쓴 것

### 5-1. 개별 문서가 아니라 **그래프**를 먼저 만든다

마이크로플로우를 하나씩 고립시켜 보면 "이거 액션이 많네요" 수준을 못 벗어납니다.
그래서 분석 전에 모델 전체를 한 번 순회해 관계 인덱스를 만들고, 이후 모든 규칙은 그 위에서 판정합니다.

```
모델 로딩 → 그래프 구축 → [로직 / 도메인 / 페이지] 병렬 분석 → 리포트
```

- 호출 그래프 + **역방향 간선**(누가 이 flow를 부르는가)
- 진입점 수집: 스케줄 이벤트 · 공개 REST/OData 서비스 · **엔티티 이벤트 핸들러** · 워크플로우 · 페이지 · 스니펫 · 레이아웃 · 네이티브 페이지 · 빌딩블록 · 네비게이션 · 메뉴
- 진입점에서 **BFS**로 도달성과 최소 깊이를 전파
- 한 번 로드한 문서를 노드에 보관해 분석기들이 다시 `load()` 하지 않도록 공유 (중복 I/O 제거)
- flow는 10개씩 배치로 병렬 로딩

> 진입점 수집이 이렇게 넓은 이유: 페이지만 훑으면 스니펫·레이아웃·메뉴·엔티티 이벤트에서만
> 호출되는 flow가 전부 "고아"로 오판됩니다. 실제로 그렇게 나왔던 것을 고친 결과입니다.

### 5-2. 같은 결함도 **어디서 실행되느냐**에 따라 값이 다르다

```
score = baseScore × (1 + 진입점가중치/10) × 깊이감쇠
```

| 진입 유형 | 가중치 | 이유 |
| :--- | ---: | :--- |
| ScheduledEvent | 10 | 무인·반복 실행. 사람이 못 본다 |
| PublishedService | 8 | 외부 호출. 호출량을 통제 못 한다 |
| EntityEvent | 7 | 커밋될 때마다 실행. 호출처가 분산돼 추적이 어렵다 |
| Workflow | 5 | |
| Page / Navigation | 3 | 사용자 조작으로만 실행 |

깊이 감쇠는 **약하게만** 겁니다(하한 0.7). 스케줄 이벤트에서 4단계 아래 flow도 실행 빈도는 진입점과 같기 때문에,
깊이는 위험도가 아니라 "책임을 묻기 쉬운 정도"로만 반영합니다.

### 5-3. XPath 파서 — "인덱스를 어디에 걸어라"를 말하기 위해

인덱스가 필요한 속성이 적혀 있는 곳은 Retrieve의 XPath 제약뿐입니다.
그래서 XPath에서 조회 키를 뽑는 파서를 별도 순수 함수로 구현했습니다.

- 문자열 리터럴과 `[%CurrentUser%]` 토큰을 **마스킹** (안에 `=`·`/`·`and`가 들어 있어 마스킹 없이는 파서가 깨짐)
- 괄호 깊이를 세어 **최상위 결합 연산자**(`and` / `or`) 판정
- 비교식 좌변 추출 + `contains()` 류 함수의 첫 인자 수집
- **직접 속성**(인덱스 가능) vs **연관 경유 경로**(이 엔티티 인덱스로는 못 푸는 것) 분리
- XPath가 참조하는 변수 수집 → 루프 이터레이터 참조 여부 판정에 사용

이 결과를 도메인 모델의 실제 인덱스 정의와 교차 검증합니다.

- **leftmost prefix 규칙** 반영: 복합 인덱스의 2번째 이후 속성은 단독 조회를 받쳐주지 못하므로, 선두 속성만 "커버됨"으로 인정
- 조회 조건이 **`or`로 묶여 있으면** 복합 인덱스가 쓰이지 않으므로 → "각 속성에 단일 컬럼 인덱스를 따로" 로 권장문구를 바꿈
- 조회 키가 **루프 안에서** 쓰였는지, **무인/외부 경로**에서 쓰였는지를 따로 세어 우선순위에 반영

### 5-4. 오탐을 줄이는 판정 — 루프 반복 상한 분석

"루프 안 DB 조회(N+1)"는 가장 흔한 지적이지만, 그대로 다 지적하면 도구가 신뢰를 잃습니다.
그래서 **반복 횟수에 상한이 있는가**를 판정합니다.

1. flow 전체를 훑어 **변수 출처 맵**을 만듦 (`db` / `memory` / `param` / `unknown`)
2. 루프가 무엇을 반복하는지 확인 — DB 조회 결과면 상한 없음, 파라미터·연관 탐색 결과면 **입력 크기로 묶임**
3. 조회 Range가 `First`인지, XPath가 루프 이터레이터를 참조하는지 함께 확인
4. 상한이 있는 경우에만 severity와 점수를 강등 (`Error` → `Warning`, 점수 ×0.5)

원칙은 **fail closed** 입니다. 변수 출처를 하나도 해석하지 못하면 등급을 내리지 않고,
"⚠️ 출처를 해석하지 못했습니다"를 근거에 명시합니다. 모르면 봐주지 않습니다.

또한 `AssociationRetrieveSource`(메모리상 연관 탐색)는 지적하지 않습니다 —
그건 권장사항이 시키는 **바로 그 패턴**이라, 여기서 잡으면 정반대 조언이 됩니다.

### 5-5. `git blame`이 안 되니 **직접 되물어본다** — 배치 이분 탐색

바이너리 모델에는 blame이 없습니다. 그래서 "그 시점에 이 결함이 있었나?"를 과거 커밋 모델을 열어 직접 판정합니다.
문제는 **커밋 하나를 여는 데 약 33초**가 든다는 점입니다.

두 가지 최적화로 해결했습니다.

1. 이슈별로 따로 탐색하지 않고, **한 번 연 모델에서 대상 이슈 전체를 동시에 판정**
2. 선형 스캔이 아니라 **이분 탐색** — 판정 결과에 따라 그룹을 좌/우로 쪼개 재귀

> 107커밋 기준 이슈당 약 7회, 두 최적화가 겹쳐 10건을 20~30회 조회로 끝냅니다.
> 조회 상한(기본 40회)에 걸리면 남은 건은 "미확정"으로 **보고**하고 넘어갑니다.

이 구조를 위해 규칙 판정을 **문서 하나만으로 재현 가능한 것**과 **전체 그래프가 필요한 것**으로 분리했습니다.
전자만 blame 대상이고, 후자(고아 flow·중복 로직 등)는 "역추적 불가"로 명시합니다.

이분 탐색 알고리즘은 콜백 주입 방식의 순수 함수로 분리했습니다.
잘못 짜면 엉뚱한 사람에게 귀속되는데, 실제 API로 검증하려면 매번 20분이 걸리기 때문입니다.

또한 커밋 메시지에서 **머지 여부를 감지**합니다. Team Server API의 커밋 객체에는 부모 커밋 정보가 없어
머지를 구조적으로 알 수 없는데, 이걸 구분하지 않으면 **"머지한 사람"이 "만든 사람"으로 리포트에 찍힙니다.**

### 5-6. 리포트는 "읽히는 형태"가 되어야 한다

초기 버전은 점수순 TOP 10 + 전체 부록이었는데, 실측 결과 세 가지 문제가 있었습니다.
지금 구조는 그걸 고친 결과입니다.

| 문제 | 대응 |
| :--- | :--- |
| 점수순 정렬이 사실상 "규칙 기본점수순"으로 붕괴 (TOP 10 중 8건이 같은 규칙, 59점 6연속) | **규칙별 섹션**으로 전환. 고치는 작업의 단위가 규칙이므로 컨텍스트 전환도 줄어듦 |
| 같은 조치 문구가 TOP 10 안에 8번 반복 | 조치는 **규칙당 한 번**만 출력 |
| 같은 flow가 1·6위, 2·7위에 중복 등장 | 중복이 아니라 **신호**였음 → `여러 규칙에 동시에 걸린 곳` 섹션으로 승격 |
| 인덱스 섹션이 리포트의 34%를 차지 | 루프 내 · 무인/외부 경로 · 조회 2회 이상만 표로, 나머지는 한 줄로 접음 |
| 모듈별 건강도에서 큰 모듈이 항상 나쁘게 나옴 | **flow당 점수**(밀도)로 정규화해 정렬 |

**"먼저 볼 것"의 설계 — 병목을 단정하지 않는다.**
정적 분석은 데이터 규모도 호출 빈도도 모르므로 "여기가 제일 느립니다"를 말할 수 없습니다.
대신 규칙마다 **정렬 축을 선언**해 리포트에 그대로 출력합니다.

> 이 규칙 안에서는 *반복 상한이 없는 것 먼저 → 커밋 지점 수* 순으로 봅니다.

읽는 사람이 "이건 일회성 마이그레이션이라 괜찮다"로 **기각할 수 있어야** 오탐이 나와도 도구가 죽지 않습니다.

### 5-7. 조용한 실패를 만들지 않는다

정적 분석 도구의 최악의 실패는 **틀린 지적**이 아니라 **룰이 죽었는데 "이슈 없음"처럼 보이는 것**입니다.
실제로 겪은 실패였고, 그래서 방어선을 여러 겹 깔았습니다.

- **`npm run selfcheck`** — 분석기가 `instanceof`로 참조하는 SDK 클래스·enum 21개가 런타임에 실재하는지 검증.
  `mendixmodelsdk`는 메타모델 변경 시 클래스를 조용히 제거하는데, `instanceof undefined`가 던진 TypeError가
  `try/catch`에 삼켜지면서 루프·복잡도·파라미터 룰이 전부 0건으로 나온 적이 있습니다. **타입 검사로는 못 잡습니다.**
- **문서 로드 실패를 집계해 경고로 출력** — 삼키면 "이슈 0건"이 성공처럼 보입니다
- **모델 전체에 인덱스 정의가 하나도 없으면** 그 사실 자체를 경고로 보고
- **마크다운 표 칸 수 일치 테스트** — 규칙마다 열 구성이 다른데 한 줄이라도 어긋나면 표가 통째로 깨지고,
  깨진 표는 "이슈가 없다"처럼 보입니다. 리포트가 조용히 거짓말하는 실패 모드라 자동으로 막습니다
- 테스트는 **자격증명 없이** 돕니다(순수 함수로 분리한 이유). 파서·이분탐색·리포터 회귀를 즉시 잡습니다

### 5-8. 지적할 수 있는 것만 지적한다

마켓플레이스·테마 모듈은 **그래프에는 남기되**(호출 관계가 정확해야 우리 코드의 도달성이 맞으므로)
지적 대상에서는 제외합니다. 남의 코드고, 고칠 수도 없습니다.

## 7. 리포트 구성

```
📌 대상 (분석 기준 리비전 · 브랜치 전체 스냅샷임을 명시)
🗺️ 모델 구성 (리뷰 대상 flow / 제외 모듈 / 진입점 분포 / 무인 실행 경로)
🎯 KPI (규칙 ID 기반 집계)
⚠️ 여러 규칙에 동시에 걸린 곳
📋 규칙별 상세 × N  (설명 → 조치 1회 → 먼저 볼 것 → 전체 표)
🔑 인덱스가 필요한 속성 (엔티티별 작업 지시서)
🏢 모듈별 건강도 (flow당 점수로 정규화)
```

리포트는 상단에 **"이 커밋이 만든 변경이 아니라 이 시점의 브랜치 전체 상태"**임을 명시합니다.
예전처럼 커밋 Author를 헤더에 박아 두면, 아래 이슈 전체가 그 사람의 것으로 읽히기 때문입니다.

인덱스 섹션에는 사실 관계도 함께 적습니다 — String 속성은 Max length가 Unlimited면 인덱스를 걸 수 없고,
인덱스는 insert/update마다 갱신 비용이 붙으므로 **목록은 후보이지 전량 적용 대상이 아닙니다.**

## 9. 알려진 한계

- **push된 것만 보입니다.** Platform SDK가 Team Server 기준이라 용도는 *사후 파악*입니다. 머지 전 사전 감지는 범위 밖입니다.
- **전수 분석입니다.** 변경분만 보는 증분 브리핑(`brief`)은 설계까지 마쳤고 미구현입니다.
- **blame은 로직·페이지 규칙만** 지원합니다. 도메인 규칙 문서 단위 재판정은 미구현, 전체 그래프가 필요한 규칙(L006/L008/D006/D007)은 구조상 불가입니다.
- **비활성 스케줄 이벤트가 가중치를 받는 경로가 남아 있습니다.** 진입점 수집에서는 `enabled`를 확인하지만, 리포트가 스스로를 반박하는 케이스가 있어 정리 중입니다.
- **KPI가 총량 기준**이라 레거시 프로젝트에서는 영원히 빨간불입니다. 증감·유입 속도 지표로 바꾸려면 스냅샷 기능이 먼저 필요합니다.
- **성능**: 모델 로딩 + 그래프 구축이 flow 400개 규모에서 수 분대입니다. blame은 커밋 조회 1회당 약 33초입니다.

## 10. 향후 계획

1. **`brief` (증분 브리핑)** — 모델 인벤토리를 스냅샷으로 저장하고 직전 스냅샷과 비교해 *"지난번 이후 뭐가 바뀌었나"* 를 출력.
   신규 지적뿐 아니라 **해결된 지적**도 함께 보고 (지적만 하는 도구는 쓰이지 않으므로).
   변경이 없으면 아무것도 출력하지 않음 — **침묵이 기본값**.
2. **알림 연동** — 개인에게는 즉시·비공개(브랜치 브리핑), 팀 채널에는 주기적·집계(개인명 없는 주간 요약).
   이 순서를 뒤집으면 도구가 공개 지적으로 읽혀 살아남지 못합니다.
3. CI 게이트(빌드 fail)는 **도입하지 않습니다** — 자동 게시보다 더 강한 공개 지적입니다.
